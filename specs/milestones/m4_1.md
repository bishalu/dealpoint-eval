# M4.1 — Execution-reliability repair and four-arm re-run (corrective, before any judging)

**Authority:** brief §1.2 (execution record, statuses), §2.2, §2.4, §6; M4 spec (frozen subset, arms,
skill, honesty rule). Inserted by the operator on 2026-09-05 after inspecting the M4 report.

## Why
The M4 results are dominated by **execution failures, not model reasoning**:
- Haiku, arm D: 16/18 `EXECUTION_FAILED` (15 `api_error`, 1 schema) while Haiku arm A mostly ran —
  so the failure is specific to the agent loop + skill path at Haiku.
- GLM 5.3 Flash, arm A (a single structured-output call): 21/32 `schema_invalid_after_retry`;
  agent arms: 4–11 schema failures and 4–10 `CAP_HIT` each.
The records carry only a coarse `failure_reason`; the loop catches every exception as `api_error`
and discards the message, and schema failures discard the model's raw text. Judging (M5) or a
Pareto (M6) on these runs would measure "which provider tolerates our request shape", not quality.

## Deliverables
1. **Evidence on every failure.** The execution record gains `failure_detail` (exception class +
   first 300 chars of the message, or the validation error) and `raw_final_text` (first 1,500 chars
   of the model's final response on schema failures). No metered call needed for this.
2. **Diagnose on 2-case probes** (≈ $0.05 total): arm D at Haiku, arm A at GLM, arm B at GLM. Read
   the captured details. Expected culprits to check first: Anthropic's limit of 4 `cache_control`
   breakpoints (the skill/playbook injection may add blocks), an unsupported field on the Anthropic
   path in arm D, `response_format` handling for non-Anthropic providers on OpenRouter (use
   `json_schema` where supported, fall back to `json_object` + tolerant extraction of fenced or
   prose-wrapped JSON), option-string matching that is too strict (quote style / whitespace — apply
   the canonical normaliser to both sides before comparing to the option list), and `max_tokens`
   too small for the final answer at some providers.
3. **Fix the harness, not the benchmark.** The frozen subset, skill files, arm configs, prompts to
   the model (question spec) and the scorers stay byte-identical (hashes asserted). Changes are
   confined to the client/loop/pipeline request shape, response parsing and record fields.
   `CAP_HIT` is a legitimate outcome and is not to be "fixed" by raising the cap.
4. **Verify** on the same 2-case probes after the fix: `EXECUTION_FAILED` rate ≤ 10% per (model,
   arm) probed; then **re-run the M4 sweeps as v2** (GLM arms A–D × 32; Haiku arms A/D × 18) with
   the spend guard, recording estimate vs realised. Keep the v1 result files and report as
   `four_arm_v1_execution_defects.*`; the new `four_arm.json`/`four_arm.md`/README carry a
   "v2 after harness repair" line and a table of failure rates v1 → v2 per (model, arm).
5. **Report notes.** State that the majority-class baseline is 0% *on this subset by construction*
   (the subset selection rule prefers cases the majority answer gets wrong) and give the majority
   baseline on the full test set alongside it for context.
