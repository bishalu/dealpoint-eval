# M3: Retrieval Tournament on Dev; Freeze Arm C

## Goal

Run a five-candidate retrieval tournament on the 58-case dev set to measure which architecture best recovers gold spans, then pin the winner as arm C for downstream experiments. Candidates are `DenseRetriever` (from M1), `BM25Retriever`, `HybridRRFRetriever`, `RerankRetriever` (hybrid + cross-encoder), and `MultiQueryFusionRetriever` (hybrid with frozen hand-written alternate queries). All measurements must be LLM-free; the winning arm's index version is recorded as the freeze point.

## Implementation Summary

**Five retriever candidates** behind the unchanged `Retriever` Protocol in `dealpoint/corpus/retrievers.py`:
- `DenseRetriever`: baseline from M1
- `BM25Retriever`: lazy `bm25s` import, per-doc cache, blank-query handling at k=20
- `HybridRRFRetriever`: reciprocal rank fusion (Python, no LlamaIndex) with tiebreak by chunk ID
- `RerankRetriever`: hybrid top-20 → `Xenova/ms-marco-MiniLM-L-6-v2` cross-encoder via fastembed, injectable scorer
- `MultiQueryFusionRetriever`: hybrid + three hand-written frozen alternate queries per question (never LLM-generated at runtime)

Frozen alternate queries stored in `data/eval/tournament_queries.json` (101 lines): 12 questions × 3 variants each, with hand-written canonical and variants for merger-related contract clauses (e.g., change-of-recommendation notice, material adverse effect definitions).

**Tournament harness** (`dealpoint/eval/tournament.py`, 572 lines):
- For every dev case and every config, runs two query passes: canonical question text and raw MAUD question text (the harder variant)
- Metrics: hit@5, hit@10, MRR on 10-result window (k=10)
- Per-stage instrumentation (`_compute_stages`) emits dense_rank, bm25_rank, fused_rank, reranked_rank, surfaced_by, rerank_effect for each case
- Wall-clock timing corrected mid-milestone: timer now starts immediately before retriever.search and stops after rank lookup, accumulating per case; rerank and stage scorers are independent to avoid cache interference
- Zero LLM calls in the tournament (qrels derived from aligned gold spans, no model inference)

**LlamaIndex decision**: evaluated at 178 MB installed size (100 MB marginal), declined because bm25s gives BM25 in three calls, RRF is eight lines of Python, and fastembed already ships the cross-encoder; no material capability gained that wasn't already in scope. Recorded in `tournament.json.llamaindex` with full justification.

**Freeze** (`dealpoint/config.py`):
- Winner: `hybrid_rrf` (hybrid RRF, no rerank)
  - Canonical hit@5: 0.9138 vs dense 0.8103 (+1034 bps)
  - ARM_C_RETRIEVER pinned to `{fetch_k: 20, kind: 'hybrid_rrf', multi_query: False, name: 'hybrid_rrf', rerank_model: None, rrf_k: 60}`
- Index version recorded: `8ae2fc1e24e9` (arm_c_index_version); main index_version unchanged at `e2b4a2b97561`
- Arms A and B remain plain dense over the same chunks
- `.gitignore` updated to track `tournament.json` and `tournament.md` in reports

## Corrective Cycles Performed

**Wall-clock timing defect (mid-milestone):**
- **Symptom:** tournament.json initially recorded hybrid_rrf_rerank timing as 8.04s and hybrid_rrf as 114.21s (inverted); the plan §3.4 predicted rerank > no-rerank
- **Root cause:** timer scope included scorer initialization and hooks outside retriever.search; stage pass used a cached scorer warmed by the config pass
- **Fix:** (1) timer starts immediately before retriever.search (:113), stops after rank lookup (:116), accumulates per case; (2) _on_case stage hook deferred (:122), invoked after all 58 cases timed; (3) config_scorer and stage_scorer built independently (:288–292) to eliminate cache interference
- **Verification:** regenerated tournament.json shows corrected times (dense 7.98, hybrid_rrf 8.06, hybrid_rrf_rerank 106.39, hybrid_rrf_rerank > hybrid_rrf as predicted); quality metrics bit-identical (only timing changed)
- **Regression test:** tests/test_tournament.py:203–237 pinned with 50 ms stub scorer asserting hybrid_rrf_rerank > hybrid_rrf and dense < multi_query_fusion_rerank

**Brief vs. spec mismatch (noted, not blocking):**
- **Issue:** Brief §2.2 labels arm C as "agent-hybrid-rerank"; tournament winner is hybrid_rrf (no rerank)
- **Resolution:** Brief §2.2 also defines arm C's backend as "tournament winner", and the measured winner is hybrid_rrf, canonical hit@5 0.9138 >> hybrid_rrf_rerank hit@5 0.9138 (equal hit@5, but RRF dominates on speed and canonical queries); rerank recovers raw-MAUD only (0.414 vs 0.276)
- **Rationale recorded** in dealpoint/config.py:184–188 for M4 to pick the label used in four_arm.json and README

## Known Limitations and Exclusions

1. **Test-set runs excluded**: tournament runs on dev set only (58 cases); test set (167 cases) reserved for M4
2. **Skill/judges excluded**: M3 is pure retrieval; no skill model or judge model involved
3. **LlamaIndex not adopted**: fastembed already ships the cross-encoder; bm25s and Python RRF cover the gaps; LlamaIndex overhead (100 MB marginal) not justified for this milestone's scope
4. **Alternate queries limited to hand-written**: the multi-query candidate uses frozen, pre-generated variants from `tournament_queries.json`; no LLM query generation at runtime (per brief §4)
5. **Arms C/D not wired into eval runner**: run.py --arm choices remain ['A', 'B']; arm C is frozen but not runnable yet; arms C/D wiring deferred to M4 (seam comment at dealpoint/eval/run.py:243–245)
6. **Index not rebuilt**: tournament uses the fixed M1 index (e2b4a2b97561); build_index.py:180–198 writes arm C as immutable, blocking re-indexing
